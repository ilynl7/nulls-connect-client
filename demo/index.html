Feature map

What the platform actually does

Every capability below is implemented and verified in the application — none of it is fabricated.

🔐

Authentication

Email + PIN sign-in via /auth/login.v2 (same game=laser&locale=ru defaults as the C client), or import an existing token.

  • Server-side sessions, HttpOnly cookie
  • Bearer token never reaches the browser
  • Centralized automatic auth on every request
🎮

Accounts & bindings

Full linked-account management for the connected identity.

  • List linked players (/games/links)
  • Per-player game tokens (/games/token)
  • Bind, transfer, refresh/revoke tokens
  • Settings + OAuth client tools
🪪

Profiles

Look up and edit profiles on profiles.dnull.xyz — including undocumented capabilities.

  • Handle / GameAccountId / hidden AccountId lookup
  • Game-token profile editor with avatar picker
  • Hidden block_friends parameter
  • Identity namespace explorer (bound vs anonymous)
🔍

Discovery workspace

An operation registry with parameters, enums, errors and evidence for every endpoint.

  • Game identifier registry + live probing
  • Image ref resolution (catalog, redirect, CDN)
  • Avatar catalog grid
  • Evidence-backed knowledge base
🛡️

Admin surface

Privileged account administration — gated behind admin tokens.

  • Whois by uid / email / scid
  • Account event timelines
  • Find by Telegram / VK
  • Admin bind / unbind
🧰

Developer tools

Everything you need to work against the API safely.

  • Per-session activity log, tokens masked server-side
  • Raw JSON views + on-demand token reveal
  • Human-readable error catalog
  • Input validation + rate limiting
  • Live upstream diagnostics

How it works

Architecture

The browser only ever talks to the same-origin backend; every upstream call is proxied server-side, with the bearer token attached automatically and never sent to the browser.

🌐 Browser

Static frontend (index.html, app.js, style.css). No CORS problem, no tokens.

→

⚙️ proxy.mjs

Zero-dependency Node backend: static server, internal API, centralized authenticated client, rate limiting, validation, error mapping, activity log.

→

☁️ Upstream APIs

connect.nulls.gg/api (auth, accounts, games, OAuth, admin) · profiles.dnull.xyz (profiles, avatars) · files.dnull.xyz (avatars).

Deep-dive example: profile /update rejects the account token (403) but accepts a per-player game token. The backend mints it from /games/token first — mirroring the C client — so the browser never handles it.

Deploy

Run the real thing in 3 commands

Zero dependencies, no build step, any Node ≥ 18 host. The server respects PORT and binds 0.0.0.0.

# on any Node host (Render, Railway, Fly, VPS, Docker…)
git clone https://github.com/ilynl7/nulls-connect-explorer.git
cd nulls-connect-explorer
PORT=3000 node proxy.mjs

# optional: build the original C CLI (needs gcc + libcurl)
npm run build:c
./output/main

Environment variables: PORT (default 3000), NC_API_UPSTREAM, NC_PROFILES_UPSTREAM. See the README for full deployment and troubleshooting guides.
